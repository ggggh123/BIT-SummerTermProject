## 抽验方式（可复现）

三段取值互相独立，任何一段对不上都能定位到层：

| 段 | 取值方式 | 对应缺陷分类 |
|---|---|---|
| ADS 真值 | 直接查 `handoff/ads/ads.db`（SQLite） | 数据 A |
| 接口值 | 拉取 `/api/*` 全量响应存档 | 接口 B |
| 大屏显示 | 无头 Chrome 打开真实页面：KPI 读 DOM 文本；**画布内数值直接从页面里的 ECharts 实例取 `getOption()`**（`web/src/components/EChart.vue` 把实例挂在 `.chart` 容器的 `__echarts` 上，本身就是为 E2E 留的口子） | 展示 C |

用「取 ECharts option」而不是「人工看截图读数」，是因为图表数据是画布像素、肉眼读数既有误差也不可复现；
取到的 option 就是图表**实际渲染的那组数**，同一条命令可以随时重跑。

### 备注（写进答辩材料的如实说明）

① **电量 0.001 kWh 差异**：`ads_daily` 逐日四舍五入再汇总得 3,430,028.399，接口/大屏取 3,430,028.4。金额是整数分所以无差异。属口径 D，不是缺陷。

② **电价均值取整**：真值 114.286 分，接口返回整数 114，大屏显示 ¥1.14/度。若要求小数位可比，需 #2 在接口层保留两位。

③ **「全城峰值负荷」是当日口径，不是窗口口径**：`/api/gov/peak-load` 只返回最近一天的 24 点（`dt=2026-09-14`），大屏 KPI 取该日峰值 7,153 kW；而窗口内真正最大是 **7,964.665 kW（2026-07-10 18 时）**，相差 10%。两个数都不错，错的是标题——老师若问「全城峰值」很容易对不上。**需要 #2/#4 定夺**：要么接口改成返回窗口峰值，要么把 KPI 标题明确为「当日全城峰值」。

④ **数据质量面板与业务指标不是同一套清洗口径**：`ads_quality_table` 的 `rows_before/after`（8 站 / 287 桩 / **112,422 单**）来自 `export_ads_db.py` 的 Python 旁路复算，而业务表的 97,804 单 / 7 站 / 251 桩来自 PRL 清洗后的 Spark 链路。两者**在同一个 `ads.db` 里并存**，`ads_meta.cleaningSource` 已写明这是「PRL §3.2 过渡口径，DWD 交付后由 SparkSQL 链路替换」。答辩时按此说明，或由 #3/#4 统一到一套口径。

⑤ **「用户增长」的新增用户全为 0**：`ads_daily.new_user_cnt` 整列 0，企业页那条新增用户曲线是一条贴地零线。原因是生成器 4,985 个用户的注册时间全部早于业务窗口（见 `ads_meta.newUserNote`），窗口期内没有注册事件。日活曲线（~900–1,050/天）正常。**答辩前需定口径**：要么让生成器在窗口内注入注册时间并重交接 ODS，要么把该图标题改为「窗口内首单新客」。
