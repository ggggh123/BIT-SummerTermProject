## 零、项目背景

### 0.1 项目来源

**东软电动汽车充电桩应用管理平台**是课程项目，按两个阶段推进：

| 阶段 | 环境与目标 | 状态 |
|---|---|---|
| **第一阶段** | Linux（Ubuntu 22.04 LTS）环境下开发 Qt/C++ 三端应用，数据底座为 SQLite | **已结项** |
| **第二阶段（本项目）** | 在 **Hadoop 分布式环境**下重建数据链路，把业务数据加工成可视化大屏与智能预测 | 本阶段 |

上游依据：`references/01.项目说明书-东软电动汽车充电桩应用管理平台.doc`、第一阶段结项成果（`docs/plans/2026-09-01-ev-charging-platform-design.md`、`database/schema.sql`）、以及指导老师提出的第二阶段七点要求。

### 0.2 第一阶段成果（本阶段的输入）

| 子系统 | 技术栈 | 状态 |
|---|---|---|
| 充电用户端 | Qt 6.2 / C++17 / 腾讯地图 Web API / QWebEngineView | 已结项 |
| PC 服务器端（管理端） | Qt 6.2 / C++17 / QTcpServer 多线程 / Socket 长度前缀 JSON 协议 | 已结项 |
| 数据库端 | SQLite（WAL、外键、唯一约束）、设备模拟器、黄金数据库 | 已结项 |

第一阶段的数据底座是 SQLite，核心表包括 `users` / `stations` / `chargers` / `orders` / `telemetry` / `station_hourly_history` / `forecast_runs` / `forecasts` / `events` / `request_log`。**两条口径被第二阶段完整继承**：金额统一整数分、时间统一 `+08:00` ISO 8601。

### 0.3 第二阶段的由来：老师七点要求

第二阶段要解决的是「**同一套业务数据，在分布式环境下怎么采集、清洗、分层、展示和预测**」。指导老师给出的七点要求构成了本阶段的任务边界：

| # | 老师要求 | 承担 |
|---|---|---|
| 1 | 安装 Hadoop | #2 TL |
| 2 | 基于第一阶段表结构生成含质量问题的模拟数据 | #4 SCML |
| 3 | 用 PySpark 发现数据质量问题 | #3 PRL |
| 4 | 用 PySpark 进行数据清洗 | #3 PRL |
| 5 | SparkSQL 完成 ODS→DWD→DWS→ADS 分层分析 | #4 SCML |
| 6 | 数据可视化：Flask + Vue + ECharts | #1 PM |
| 7 | 数据预测：Spark MLlib（**老师标注选做，本组按必做标准完成**） | #5 PE |

**为什么选这个题目**：第一阶段的 SQLite 单体架构能验证业务正确性，但数据量只有万级、全部在单机；第二阶段把数据规模提到 **百万级遥测 / 12 万订单**，并强制走 HDFS + Spark 分布式链路，才能真正暴露「数据质量、数据倾斜、资源约束、口径一致」这类工程问题。

### 0.4 四条设计原则（贯穿全程的硬约束）

1. **复用第一阶段资产**：表结构、枚举口径（桩状态、订单状态、金额分、ISO 时间）、站点与业务规则全部沿用；模拟数据生成器**直接以 `database/schema.sql` 为契约**，不另立标准。
2. **先闭环后增强**：优先打通「生成 → 入 HDFS → 清洗 → 分层 → API → 大屏」一条完整主干，再逐层加图表与预测，避免最后一刻才发现链路不通。
3. **确定性可复现**：固定随机种子，同版本重复生成的数据哈希一致，答辩可现场重建。
4. **不作虚假声明**：所有页面标注「项目生成的模拟数据」；选做任务若未完成，大屏显示「暂无预测」而不是伪造数据。

## 一、项目功能

**一句话概括**：把充电桩运营的模拟业务数据，从原始落盘一路加工到可视化大屏与智能预测，全流程可复现、可对账、有证据。

| 功能模块 | 具体内容 |
|---|---|
| **模拟数据生成** | 8 站点 / 288 充电桩 / 5,000 用户 / 120,000 订单 / 1,000,000 条遥测 / 20,000 事件 / 90 天业务窗口；**主动注入 10 类质量问题（R01–R10）共 32,775 条**，让「发现质量问题」有真实靶子而不是空跑 |
| **数据质量检测** | PySpark 离线检出 10 类问题：缺失值、重复记录、异常值、时间格式混杂、逻辑矛盾、金额口径错误、孤儿外键、非法枚举、经纬度越界、文本脏数据；逐类给出 TP / FP / FN 与召回率 |
| **数据清洗与分层数仓** | 清洗链路（PRL）→ **DWD 7 张表 → DWS 4 张表 → ADS 8 张表**，四层全部落 Parquet，**7/7 写后读回断言零违规** |
| **交接机制** | 每个环节产出 `manifest.json`（表级行数 + 逐文件 SHA-256 + `run_id` + 数据窗口 + 契约/策略版本），接收方校验通过后才消费；大体积数据与交接包不入 Git，按约定走共享目录 |
| **数据可视化大屏** | **5 个页面**（主页 + 充电站 / 企业 / 政府 / 用户视角）、**20 个图表**、**28 条只读 API**；轮询刷新，后端异常时保留上次成功数据并提示过期，不白屏 |
| **智能预测** | Spark MLlib 直接式多步预测：对未来 **24 个 horizon** 预测站点负荷与占用桩数，派生空闲桩数、拥堵等级、高峰时段，产出 3 张 ADS 预测契约表（`is_baseline=0` 表示真实 MLlib 批次，`1` 表示 seasonal-naive 基线降级） |
| **缺口防护**（本轮补强） | 小时级数据存在缺失整点时，训练前先做**整点网格对齐**，使 `lag/lead/rolling` 的行偏移严格等价于时间偏移，并配套覆盖核验门禁 |

## 三、项目心得（问题 → 收获）

> 每条都来自本项目的真实事件，可在 `part2-defect-log.md` 与代码注释中查证。

**1. 小时表缺了 47 个小时，行偏移特征会静默错位**
`lag_24h` 的语义是「第 24 行之前」，不是「24 小时前」。序列中间缺一格，特征和标签会一起错位，**而且不会报任何错**。
→ **收获**：用行偏移做时序特征前，必须先核验时间连续性；把核验写成门禁（覆盖核验 + 网格对齐），不要依赖人记得。

**2. 一次重构把模型退化成单特征，指标从 33 恶化到 177.6，全程零报错**
把「特征可用性判定」错作用在原始表上，与派生特征名的交集只命中 1 列，模型静默退化为单特征训练。
→ **收获**：管线改完必须跑端到端回归并**比对指标**。「跑得通」不等于「算对了」——**指标异常是发现静默错误的主要手段**。

**3. 低内存 executor 在最后一步 OOM**
把 24 个模型的 `transform` 直接 `union` 成一条长 lineage，Spark 会把所有树模型一次性序列化给同一个 executor，小内存机器在最终 write 时崩。
→ **收获**：模型数量多时按 horizon 逐个物化成有明确上限的小结果再重组；**长 lineage ≠ 高性能**。

**4. 「对账失败」其实是对账自己错了**
对账脚本拿本地清洗实现去重算**未清洗的 ODS**，再与清洗后的 ADS 比较，必然差出 8,580 万元营收；一开始全组以为是数据算错。
→ **收获**：对账两边必须**同源同口径**，否则对账本身会制造假告警，反而掩盖真问题。

**5. 大屏显示「检出 0」，第一直觉是检测漏检，实际是注入端有 bug**
R02 重复记录注入 11,200 条却检出 0。逐层核查才发现：生成器注入重复行时跳过了业务主键，导致「重复行」主键各不相同，检测端按业务主键分组永远命中不到；同时 ADS 侧的计数口径也写窄了。
→ **收获**：看到「检出 0」先分清**注入端 / 检测端 / 展示端**是哪一层的问题，不要顺着第一直觉下结论。

**6. 改一条清洗契约，炸了两个地方**
Q9 从「隔离越界站点」改为「仅置空坐标」后：① 两处必填断言未同步，PRL 连挂两轮；② 用户页接口 `float(None)` 崩溃，**整页 4 个图表全部空白**。
→ **收获**：改契约要同步扫**所有下游消费方**；并且必须做**页面级**验证——接口单测全绿也发现不了「整页空白」。

**7. 跨机复现时，别急着重装工具链**
集成分支的安装脚本假设一套独立环境（Hadoop 3.2.1 + JDK 8），与本机已验证的 Hadoop 3.4.1 + JDK 17 冲突，且脚本拒绝覆盖已存在目录。
→ **收获**：优先写一层**只读兼容 shim** 复用既有环境，而不是改上游脚本或推倒重装；上游代码一字不动，他人也能复用。

**8. YARN 作业长期停在 ACCEPTED，不是卡死**
队列的 AM 资源上限只允许 1 个 ApplicationMaster，第二个作业只能排队，日志里没有任何错误提示。
→ **收获**：资源类「卡住」先查调度器限制（`maximum-am-resource-percent`），不要急着重试或怀疑代码。

**9. 契约没冻结时脚本拒绝出正式产物——这是好事**
起初觉得 `--accept-draft` 这类门禁很碍事，后来发现它恰好挡住了「看起来成功、其实口径未确认」的交付。
→ **收获**：把数据前提与契约状态做成**硬门禁**，比写在文档里靠人自觉可靠得多。

**10. 同一个库里并存两套清洗口径，指标必然对不上**
`ads.db` 里业务表走 PRL 清洗（110,696 单 / 8 站），质量面板的 `rows_before/after` 却来自旁路复算（120,000 单），两套数同框展示必然引发质疑。
→ **收获**：口径必须**单一来源**；过渡期至少要用 `ads_meta.cleaningSource` 这类字段显式标注，并在答辩口径里说清楚。
