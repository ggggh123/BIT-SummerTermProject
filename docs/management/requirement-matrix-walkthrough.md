## 一、总：项目逻辑（先讲这条链，五大板块自然就出来了）

### 1. 命题与硬约束

东软命题《电动汽车充电桩应用管理平台》：5 人、9 天（9/1–9/10）、必须交付五个**全部可运行**的子系统。三条硬约束决定了我们所有技术选型：

1. **没有真实充电桩、没有真实业务后台、没有外部数据源** —— 所以一切业务历史、设备遥测、天气节假日特征都由**项目内的确定性模拟器**生成，答辩时如实说明"这是模拟数据"。
2. **指定技术栈**：Ubuntu 22.04+、Qt 6（C++）、SQLite、Socket 通信、主框架多线程、Web 端 ECharts、用户端调用腾讯地图、ML 输出 1h/6h/24h 预测。
3. **评分看现场演示**：所以交付策略是先打通一条**稳定、可复现、跨五系统的数据闭环**，再叠加界面表现。

### 2. 一条业务链讲清整个系统

充电业务的本质一句话：**车主找桩 → 充电 → 付钱**。把这句话在"没有真实设备"的前提下跑通，就得到我们的数据流：

```
[设备模拟器] --每3秒遥测/故障事件--> [Qt 服务端] --事务写入--> [SQLite 数据库]
                                        │
                                        ├--原子替换--> dashboard_snapshot.json --> [Web 大屏]
                                        ↑
[ML 预测] --forecast.publish(144条)-----┘
                                        │
[Qt 用户端] <----预约/充电/结算/推荐----┘
[管理界面] <----同一套业务服务层---------┘
```

三个关键设计决策（评委必问，提前说）：

- **服务端是 SQLite 的唯一在线写入者**：所有预约、充电、计费、结算、冻结都由服务端业务层校验后串行写库，其他任何进程（模拟器、ML、大屏）都不碰数据库——这是数据一致性的根。
- **大屏只读快照**：服务端每次成功业务事务后把新 JSON 原子替换到 `dashboard_snapshot.json`，大屏 2 秒轮询它；大屏失败就保留最后成功数据并显示过期，绝不写任何业务数据。
- **ML 只读训练快照、只经协议发布**：预测结果通过 TCP `forecast.publish` 交给服务端校验（必须恰好 144 条）后单事务入库；失败保留 `forecast_last_good.json` 不覆盖旧版。

### 3. 于是五大板块自然成形

沿着这条链，需求矩阵切成五大类——**这不是拍脑袋分的，是数据流上每个角色各占一段**：

| 大分类 | 在链上的位置 | 负责人 |
|---|---|---|
| 充电用户端 | 业务的起点：车主操作的一切 | 胡晟源 #3 |
| PC 服务器端 | 链的枢纽：所有规则的裁判 + 唯一写入者 | 杨佳车 #2 |
| 数据库端 | 链的地基：数据存哪、怎么安全流动、设备数据从哪来 | 倪宇骏 #4 |
| 大数据可视化大屏 | 链的出口：让数据被看见 | 王浩恩 #1 |
| 机器学习智能分析 | 链的大脑：从历史数据预判未来 | 庞项祯 #5 |

需求矩阵 23 条小分类，就是把这五个角色各自"必须做到的事"逐条拆成可验收的功能点。下面逐板块展开。

## 二、板块一：充电用户端（NO.1–8，胡晟源）

**板块定位一句话**：用户视角的第一米——从"我在哪、附近有什么桩"到"插枪充电付钱离场"的完整旅程。

**中分类怎么来的**：跟着用户操作顺序自然拆四段——**先找到桩（充电站查询）→ 到了要导航（一键导航）→ 是谁在用（用户信息维护）→ 真正充电（电动汽车充电）**。8 条小分类全部对应 `user-client.md` 实施计划的具体任务。

### 1.1 位置定位（NO.1）

- **实现**：不依赖真实 GPS——用户下拉选区域或手动输入地址；输入地址时用 `QNetworkAccessManager` 调**腾讯地图地址解析 WebService（geocoder）**把地址转经纬度；Key 从本地 `config.local.ini` 读取，绝不硬编码进源码；解析失败/超时给出明确的中文错误并支持重试。
- **对应实现**：`user-client.md` Task 4；`feat/user` 分支已提交 `TencentMapClient` 相关代码。
- **演示点**：输入"学院路"→ 拿到经纬度 → 附近站列表自动按距离刷新。

### 1.2 附近电站列表展示（NO.2）

- **实现**：调 `station.list {latitude, longitude}` 拿全部站点；客户端用 **Haversine 公式**算当前位置到每站的球面距离，按由近到远排序；每张站点卡片显示**站名、价格（元/度）、桩总数/空闲数、距离（公里）**。
- **演示点**：6 个种子站（阳光/学院路/西二旗/亦庄/望京/通州）按距离排列，卡片数据与数据库实时一致。

### 1.3 电站详情查看（NO.3）

- **实现**：点击卡片触发 `station.detail {stationId}` + `charger.list {stationId}`；详情页展示站点信息与**该站全部电桩明细**（编号、快充/慢充类型、当前状态、功率），空闲桩高亮可选。

### 1.4 地图导航集成（NO.4）

- **实现**：点击列表中的距离信息进入导航——`QWebEngineView` 加载项目内置的 `resources/map/navigation.html`（已在 `feat/user` 分支提交），该页面调**腾讯地图 JavaScript API GL**；起点=当前位置、终点=目标电站坐标；支持**驾车/步行切换**重新规划路线。
- **风控点**：Key 失效/网络异常时显示原因与重试按钮，保留最后成功路线；**绝不冒充实时调用**。

### 1.5 免密登录/注册（NO.5）

- **实现**：只输 11 位手机号（正则 `^1[3-9]\d{9}$` 校验）；调 `auth.user_login`：手机号已存在 → 直接登录返回 token；不存在 → **自动创建新用户**，默认昵称"用户+手机号后4位"。零密码、零验证码，把使用门槛降到最低。

### 1.6 个人信息展示与修改（NO.6）

- **实现**：登录后展示默认灰色头像、昵称、钱包余额（元）；`user.update` 修改昵称实时落库；`wallet.recharge` 输入金额模拟充值（输入最多两位小数，转整数分），余额实时更新。头像上传持久化按已确认范围不实现（答辩如实说明）。

### 1.7 充电前检查（NO.7）

- **实现**：进入充电页面前先调 `order.current` 查当前用户是否有"充电中"的未完成订单；**有 → 弹窗"您有未完成的充电订单，请先结算"并强制跳转结算页**；无 → 正常进入选桩流程。这是防"僵尸订单"的关键守卫。

### 1.8 充电操作与计费（NO.8）

- **实现**：完整闭环 `charge.reserve`（预约，仅空闲桩）→ `charge.start`（开始，校验冻结/余额/桩可用）→ 每 3 秒遥测由服务端按**累计电量 × 站点单价**动态计费 → `charge.stop`（写结束时间）→ `charge.settle`（扣款结算）。**金额由服务端算，客户端无权提交最终金额**；余额不足转待处理，充值后完成结算；历史订单可查。

## 二、板块二：PC 服务器端（NO.9–18，杨佳车）

**板块定位一句话**：整个系统的**裁判 + 账房 + 唯一写入者**——所有业务规则在这一层校验，所有数据变更从这一层落库。

**中分类怎么来的**：拆成两类职责——**对人的管理界面**（管理员登录、销售业绩、电桩状态、充电桩管理、充电站管理、用户管理）和**对系统的通信底座**（多线程 TCP、事务、鉴权——对应数据库端的"通信与安全"）。对应 `admin-server.md` 的 7 个任务。

### 2.1 管理员登录／身份验证（NO.9）

- **实现**：`admin.login`，账号密码存数据库管理员表（默认 `admin / 123456`，密码 SHA-256 比对）；登录成功返回 admin token 进主界面；**本地管理界面与 TCP 服务共享同一套业务服务层**，管理操作不走后门。

### 2.2 销售业绩／营收趋势展示（NO.10）

- **实现**：`admin.dashboard {rangeDays: 7|30}` 聚合 SQLite 出近 7 日/近 30 日营收，**Qt QChart 折线图**展示，可切换时间维度；与管理端 KPI、Web 大屏数值三方一致（同一数据库口径）。

### 2.3 销售业绩／核心指标展示（NO.11）

- **实现**：今日营收、本月营收、总营收三大核心数字；整数分存储、前端格式化千分位+元号；与 `dashboard_snapshot.json.kpis` 同源同值。

### 2.4–2.5 电桩状态分布 + 充电桩列表（NO.12–13，实现为同一个管理视图）

- **设计决策（2026-09-03 组长确认）**：两者**合并为同一个充电桩管理视图**——顶部五态统计条（空闲/已预约/充电中/故障/重启中的数量与占比，**可点击**），点击任一状态即筛选下方全量充电桩表（默认"全部"）；管理员在表中选中故障桩执行远程重启（仅 fault 可重启）。
- **为什么合并**：状态计数与桩明细出自同一数据库口径，分成两页反而重复；合并后"看健康度 → 定位桩 → 处理"一气呵成。
- **说明书的两个功能点都保留**：状态数量+占比 ✓、桩列表字段（编号/电站/类型/功率/状态/累计次数/累计时长）✓、远程重启 ✓——需求矩阵 NO.12/13 保持两行不变，只是实现落点在同一页面。
- **口径与 Web 大屏一致**：状态计数与环图同源，数字永远对得上。

### 2.6 充电桩管理／远程重启操作（NO.14）

- **实现**：选中故障桩执行 `admin.charger_restart`，状态机 **fault → restarting → idle**（模拟向桩发重启指令处理死机）；操作写入事件表留痕，管理端与事件流同步可见。

### 2.7 充电站管理／充电站列表与详情（NO.15）

- **实现**：列表含充电站 ID、站名、详细地址、经纬度、总电桩数、**当前在线率**；点击行看该站所有电桩实时状态明细；含 `forecastEnabled` 标记（哪 6 站参与预测）。

### 2.8 充电站管理／新增电站（NO.16）

- **实现**：填写站名、地址、经纬度、单价、快/慢桩数完成新增；**新建站 `forecastEnabled` 默认 false**——照常参与查询/营收/状态统计，但不进 ML 预测范围（保证 144 条预测契约不被打破）。

### 2.9 用户管理／用户列表与查询（NO.17）

- **实现**：用户 ID、手机号、昵称、钱包余额、注册时间、状态（正常/冻结）；**手机号模糊搜索** + 分页（`admin.user_list {mobileLike, limit, offset}`）。

### 2.10 用户管理／用户状态管理（NO.18）

- **实现**：`admin.user_set_status` 切换正常/冻结；**冻结用户不能预约、不能充值、不能开始充电**（业务层强制校验，不是前端摆设）；操作留痕。

### 板块补充：服务端同时扛着"通信与事务"底座

虽然需求矩阵把"通信与安全"归在数据库端，实现上它由服务端承载：**多线程 QTcpServer**（连接工作线程解析帧）+ **DatabaseWorker 唯一写线程**串行执行所有 SQL + 每次成功事务**原子替换 Web 快照** + 17 个错误码 + `request_log` 幂等审计。这是 NO.20 的实现主体。

## 二、板块三：数据库端（NO.19–20 + 设备模拟，倪宇骏）

**板块定位一句话**：链的地基（数据存哪、怎么约束）+ 发动机（设备数据从哪来）+ 免疫系统（数据怎么安全流动）。

### 3.1 数据存储／数据库设计（NO.19）

- **实现**：SQLite v1 Schema，**14 张表**（用户、管理员、站点、充电桩、订单、遥测、小时级历史、预测批次、预测明细、事件、请求日志、快照版本等）+ 外键 + CHECK 约束 + 部分唯一索引（一用户一活动订单、一批次唯一 active 预测）；`schema_version` 版本表；WAL 模式 + 外键 + 3000ms busy timeout。
- **确定性数据**：固定种子 `20260901` 一次生成 **6 站 / 48 桩 / 30 用户 / 30 天已完成订单 / 90 天 × 24 小时 × 6 站 = 12,960 行 ML 训练历史**；相同 seed 重复生成数据哈希一致（可复现，答辩可现场验证）。
- **黄金库机制**：`build_golden.py` 生成基础库 → ML 批准后 `finalize_golden.py` 导入批准的 144 条预测生成最终 `demo.db` + SHA-256 清单 + `integrity_check`；一键复位脚本从黄金库恢复演示起始状态，**现场绝不手改数据库**。
- **落地状态**：`feat/data` 分支已提交 `schema.sql / seed_demo.py / build_golden.py / finalize_golden.py / export_ml_history.py` 全套 + 测试。

### 3.2 数据处理／通信与安全（NO.20）

- **通信**：自定义**长度前缀 JSON/TCP 协议**——4 字节无符号大端长度 + UTF-8 JSON，单帧上限 1 MiB；增量式解码正确处理半包/粘包；非法长度/非法 JSON/不支持版本立即返回协议错误并断开。
- **安全**：27 个动作 × 4 角色令牌（user/admin/simulator/ml）的**权限矩阵**，服务端先鉴权再进业务；17 个错误码（`AUTH_REQUIRED / FORBIDDEN / INSUFFICIENT_BALANCE / FORECAST_INVALID`…）；`request_log` 表记录每次变更请求实现幂等与审计。
- **错误处理**（说明书 §2.3 要求）：完整错误处理机制——协议层/业务层/前端展示三层错误都有明确中文提示。
- **落地状态**：`feat/web`（#2 提交）已含 `shared/contracts`（Actions/Statuses/Permissions）、`shared/protocol`（FrameCodec/JsonEnvelope）+ Qt Test 全套，`interface-contract.md` 已冻结。

### 3.3 设备数据模拟（矩阵外的必要补充，主动向老师说明）

说明书的业务数据没有真实来源，因此我们把"设备"做成了**可视化模拟器**（五系统交付之一，Data Task 4–6，已实现于 `feat/data`）：

- 可视化控制面板：启动/暂停、模拟时钟、事件计数、充电桩表。
- 每 **3 秒**向服务端推送一批遥测（`telemetry.push`：功率、电量增量、状态），推动电量与金额真实增长。
- **故障注入与恢复**（`simulator.fault_set`）：可现场制造/修复故障桩，验证管理端远程重启闭环。
- 模拟器**永不打开数据库**、永不提交权威金额，只发设备事件——数据权威始终在服务端。

## 二、板块四：大数据可视化大屏（NO.21，王浩恩）

**板块定位一句话**：让链上所有数据**被看见**——运营决策者的实时健康度看板，答辩时全场目光的焦点。

**中分类只有一条"数据展示／业务健康度看板"，但它展开为八个子模块**（对应 `web-dashboard.md` Task 1–6，已全部实现并推送 `feat/web`）：

### 4.2 近 7 日营收趋势
柱状图，7 个数据点（08-26 ¥16,800 → 09-01 ¥24,900），横轴日期标签自动生成。

### 4.3 24h 实际负荷 + 未来 24h 预测双曲线
**本屏的招牌图**：过去 24h 实际负荷（144 点 = 6 站 × 24h）与未来 24h 预测（144 条）拼在一条时间轴上，预测段虚线/异色，**"高峰"两点标记**（模型预测的最大连续 2 小时）；支持站点下拉切换。

### 4.7 实时事件流
开始充电/订单完成/桩故障/预测发布/远程重启五类事件，时间 + 类型标签 + 消息，**textContent 节点渲染防注入**。

### 4.8 2 秒轮询与降级（工程亮点）
- 先校验后渲染：19 项契约规则（版本、144/144 长度、状态和=总数、占用+空闲=容量、ISO 时间…）不过关的数据**永远不上屏**；
- 每 2 秒同源轮询，**新版本号才整页原子重绘**，同版本心跳只刷时间；
- 连续 10 秒失败 → 显示"连接超时·保留最后成功数据"；首载失败 → 加载缓存演示快照并标注 `cached` 非实时；
- **全本地静态资源，断网也能演示**（ECharts 已本地化，无任何 CDN）。

## 二、板块五：机器学习智能分析（NO.22–23，庞项祯）

**板块定位一句话**：从 90 天历史里学会"明天哪个站会堵"，让用户端会推荐、运营端会预警。

### 5.1 负荷智能预测（NO.22）

- **数据**：只读数据库导出的 12,960 行确定性历史 CSV（6 站 × 90 天 × 24h），特征含小时、星期、周末/节假日、模拟温度、1h/24h 滞后与 6h/24h 滚动统计。
- **切分纪律**：按时间顺序 62 天训练 / 14 天验证 / 14 天测试，**禁止随机打乱、禁止未来数据泄漏**。
- **模型**：以"昨日同一时刻"为 seasonal-naive 基线，与 **Ridge 回归**按验证集如实对比——**若 Ridge 不优于基线就部署基线并如实标注**（不吹嘘）。
- **产出**：每站未来 24 小时点，共 **144 条预测**，突出 1h/6h/24h 三个档位；报告负荷 MAE/WAPE 与空闲桩 MAE。
- **物理约束**：负荷∈[0, 额定功率]、占用∈[0, 桩数]、空闲=总数−占用、无 NaN；标记未来 24h 预测负荷最大的**连续 2 小时**为高峰；占用率 ≥80% 标高拥堵。

### 5.2 智能推荐与预警（NO.23）

- **发布链路**：`forecast.publish` 经同一 TCP 帧协议批量提交，服务端校验恰好 144 条后**单事务入库**（同 run_id 幂等）；发布失败保留 `forecast_last_good.json` 不覆盖上一版成功结果。
- **用户端消费**：`forecast.latest` 读取 1 小时预测，展示"预计空闲桩"与拥堵等级，**优先推荐低拥堵站点**减少排队。
- **运营端消费**：管理端与大屏展示预测高负荷站点，占用率 ≥80% 触发负荷预警，辅助电力调配与值守安排。

## 四、备查：评委可能的提问与应答口径

| 可能的提问 | 应答口径 |
|---|---|
| "数据是真的吗？" | 如实：全部由确定性模拟器生成，固定种子可复现，答辩数据冻结在 2026-09-01 09:00 基线；这正是我们设计模拟器的目的——在没有真实设备的条件下验证全链路。 |
| "为什么服务端只有一个写入者？性能不会差吗？" | 一致性优先：单写入者 + 串行事务消除并发写冲突，演示规模（48 桩、3 秒遥测）下完全够用；这是 SQLite 官方推荐的使用模式（WAL + busy timeout）。 |
| "ML 为什么用 Ridge 不用深度学习？" | 90 天 × 6 站的数据量下，Ridge 与基线可解释、可复现、可物理约束；我们如实对比，若 Ridge 不优就部署基线——诚实比堆模型重要。 |
| "大屏挂了怎么办？" | 保留最后成功快照 + 明确的 stale/cached/error 标签；19 项契约校验保证坏数据不上屏；ECharts 本地化，断网可演示。 |
| "预测为什么是 144 条？" | 6 个启用预测的种子站 × 24 小时 = 144，服务端强校验，多一条少一条都拒绝入库；新增站默认不参与预测，契约恒定。 |
| "手机号不用密码安全吗？" | 演示场景的免密设计降低使用门槛；生产化需叠加短信验证——范围决策在需求确认阶段已记录（scope-baseline.md）。 |
