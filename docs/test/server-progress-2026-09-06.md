## 4. 必须优先处理的问题

本记录中的 P0 表示阻断真实核心闭环或造成金额错误；P1 表示影响稳定联动、异常路径或展示可信度。

### P0-1：业务时间戳不符合合同，实际 Qt 客户端拒收

实际输出：

```text
黄金库老用户：Qt UserApi loginSucceeded
预约：服务端 ok=true，reservedAt=2026-09-06T02:14:01
客户端：chargeRequestFailed INVALID_RESPONSE，uncertain=true

新手机号：服务端 ok=true，registeredAt=2026-09-06T02:14:01
客户端：requestFailed INVALID_RESPONSE
```

原因：`AuthService.cpp:73`、`UserService.cpp:14` 等使用本地时间 `toString(Qt::ISODate)`，在本机即便 `TZ=Asia/Shanghai` 也不输出时区偏移；字段又被直接返回。合同要求显式 `+08:00`，本机 `ContractTimestamp.cpp` 和 `UserApi.cpp` 按此校验。

影响不仅是显示格式：预约在服务端已经成功，客户端却无法接受结果，只能标记“结果未确认”；盲目再点预约可能制造二次操作困惑。应由服务端统一格式化业务时间并检查注册、桩更新、订单各阶段时间，不通过放宽客户端解码掩盖问题。黄金库既有的合法注册时间解释了“老用户登录成功、新用户失败”的差异。

### P0-2：停止充电覆盖累计电量/金额，时长仍有固定值

真实服务端流程：预约 → 开始 → 两次遥测（0.25 + 0.50 kWh）→ 停止 → 结算。

| 字段 | 停止前 | 停止后 |
|---|---:|---:|
| `energyKwh` | 0.75 | 1.00 |
| `amountFen` | 113 | 100 |
| `elapsedSec` | 0 | 3600 |

开始和停止发生在同一墙钟秒。`UserService::stop` 仍写死 `energy_kwh=1.0/amount_fen=100`；订单返回时长和结算累计时长也有 0/3600 常量。新增遥测计费与旧用户流程没有统一。

修复验收应要求停止保留遥测累计量、金额遵循合同的四舍五入公式、时长来自实际权威时间。`charge.stop` 后订单仍为 `charging`、带 `endedAt` 等待结算是合同规定，不是本问题。

### P0-3：请求日志不等于幂等重放，重复充值已经发生

同一 `requestId`、同一充值金额 100 分连续发送两次：

```text
原余额 50000 → 第一次 50100 → 第二次 50200
两次均 ok=true，响应字节不相同
```

重复的同一遥测请求则第一次成功、第二次返回 `ORDER_STATE_CONFLICT`，没有重放原 ACK。

`ApiServer.cpp:104` 先执行业务再记日志；`RequestLogService.cpp:101` 的 `INSERT OR IGNORE` 只防止日志重复，不能撤销已经重复执行的业务。应在再次执行业务/校验设备 cursor 之前返回首次已提交响应，并让业务变更与相关持久化提交保持原子性。

此外，`start/settle/cancel` 中存在多条 SQL 没有完整事务包裹、部分 `exec()` 返回值未检查的静态风险。本次没有注入 SQLite 故障来证明部分提交，不能将这一风险写成已复现的数据损坏。

### P1-1：模拟器 R14 的内存递增没有保留到线上

数据分支在内存中给连续事件增加毫秒，但 `SimulatorClient.cpp:13` 仍用 `Qt::ISODate` 编码。Qt 实际验证：

```text
2026-09-06T01:00:00.001+08:00 → 2026-09-06T01:00:00+08:00
2026-09-06T01:00:00.002+08:00 → 2026-09-06T01:00:00+08:00
```

服务端实际拒绝同秒相同线上时间的故障恢复，返回 `ORDER_STATE_CONFLICT`。因此不能仅凭内存时间比较测试就关闭 R14。应验证真实编码后的遥测、故障和恢复消息仍严格递增；不能取消服务端合理的时间顺序校验。

### P1-2：运行联动与现场启动还需要补齐

- 模拟器主要在连接、运行/暂停和手动刷新时取得权威桩快照。用户端开始/停止及管理端重启后，可能继续使用旧桩状态。首轮验证必须显式刷新并记录这一条件；最终应提供可靠同步路径。
- 模拟器默认 token 为空；当前服务端要求模拟器身份。诊断启动使用 `--token sim-token`，这是现有代码中的测试凭据，不是腾讯 Key。
- 管理端 `main.cpp:15` 把 `--db/--host/--port/--snapshot` 也当作无界面模式触发条件。当前“带黄金库路径启动”不等于“显示管理界面”。正式彩排必须先明确 GUI 与 headless 的配置入口，不能另起一个默认数据库的 GUI 冒充同库管理端。
- 月营收目前直接使用总营收，告警数组固定为空，部分管理页没有自动刷新。金额统计口径及充电/故障后的管理页刷新，比继续加页面更值得优先处理。
- 未结算故障订单在桩恢复 idle 后的再次预约，服务层缺少完整占用检查；数据库唯一约束仍会挡住重复 active order，但会暴露 `DB_ERROR`，不是合同规定的业务拒绝。本次是静态检查结论，不宣称已经创建双重订单。

### P1-3：黄金库封存不等于演示复位已经完成

仓库尚无可用的自动演示复位入口；模拟器的复位准备只是暂停，不会恢复数据库。`demo.reset` 已在冻结合同第 27 条和 shared 权限表定义，但当前服务端没有实现。原探针使用用户身份和空 payload，其返回“未支持”只记录当前路由表现，不能替代管理员携带合法 confirmation 的验收。此处是既有合同实现缺口，不需要新增或改名 action。

可以先采用受控人工流程：退出三端 → 校验黄金库 → 生成新的运行副本 → 启动唯一服务端 → 客户端和模拟器重新连接。不得在运行时直接覆盖 SQLite 文件。

另外，`database/build_golden.py` 默认写 `manifest.json`，没有自动生成当前封存命名的 `core.manifest.json/core.db.sha256`；直接对旧黄金目录执行重建可能覆盖旧 manifest。应在独立输出目录重建，再明确发布文件名与校验值。
