## 1. 第二阶段背景与目标

### 1.1 第一阶段回顾（已结项）

第一阶段已在 Linux（Ubuntu 22.04 LTS 基线）环境下完成三个核心子系统的开发与结项：

| 子系统 | 技术栈 | 状态 |
|---|---|---|
| 充电用户端 | Qt 6.2 / C++17 / 腾讯地图 Web API / QWebEngineView | 已结项 |
| PC 服务器端（管理端） | Qt 6.2 / C++17 / QTcpServer 多线程 / Socket 长度前缀 JSON 协议 | 已结项 |
| 数据库端 | SQLite（WAL、外键、唯一约束）、设备模拟器、黄金数据库 | 已结项 |

第一阶段数据底座为 SQLite，核心表包括 `users`、`stations`、`chargers`、`orders`、`telemetry`、`station_hourly_history`、`forecast_runs`、`forecasts`、`events`、`request_log` 等（详见 `database/schema.sql`），金额统一整数分、时间统一 `+08:00` ISO 8601。

### 1.4 设计原则

1. **复用第一阶段资产**：表结构、枚举口径（桩状态、订单状态、金额分、ISO 时间）、站点/业务规则全部沿用，模拟数据生成器直接以 `database/schema.sql` 为契约。
2. **先闭环后增强**：优先打通「生成 → 入 HDFS → 清洗 → 分层 → API → 大屏」一条主干链路，再逐层加图表与预测。
3. **确定性可复现**：固定随机种子，同版本重复生成的数据哈希一致，答辩可现场重建。
4. **不作虚假声明**：所有页面标注「项目生成的模拟数据」；选做任务若未完成，大屏预测模块显示「暂无预测」而不伪造。

### 2.3 与第一阶段的关系

- 第一阶段 SQLite 黄金库是**口径参考与表结构契约**，第二阶段不直接在线读取它，而是按同构表结构**重新生成大规模模拟数据**（第一阶段仅 6 站 48 桩 30 用户，第二阶段扩到 8 站约 300 桩 5000 用户 12 万+ 订单）。
- 第一阶段 Qt 三端不在第二阶段改动；第二阶段是独立的 Hadoop/Spark/Web 技术栈项目。**部署形态为「5 台成员机各自安装单机伪分布式 Hadoop、互不组网 + 一台集成/演示机跑全链路」**，数据与产物经共享文件夹/网盘交接（见《02》§2.4）。
- 预测口径沿用第一阶段：未来 1h / 6h / 24h 的站点负荷、空闲桩、高峰时段，拥堵等级 `low/medium/high`，评估指标 MAE / WAPE，禁止未来数据泄漏。

### 2.4 部署形态与集成/演示机

**部署形态**：5 台成员机各自安装**单机伪分布式** Hadoop（互不组网），全链路集成与答辩演示固定在一台**集成/演示机**上完成；数据与产物经共享文件夹/网盘交接。集成机**不是多节点集群，也不是特殊机型**。

**（1）集成机是「角色」而非「机型」**：除多装应用层依赖与收齐交接包外，集成机与成员机**使用完全相同的环境基线**（JDK 17 / Hadoop 3.4.1 / Spark 3.5.7 / 端口与路径一致），任何一台 `check_env.sh` 全绿的成员机均可直接担任，**无需重装 Hadoop**。

| 项 | 成员机 | 集成/演示机 |
|---|---|---|
| 环境基线（JDK / Hadoop / Spark / 端口 / 路径） | 必须一致 | 必须一致，**不重装** |
| HDFS 业务目录 `/ev-charging/*` | ✅ | ✅ |
| Python 依赖 | `pyspark` 为主 | 增 `flask`、`flask-cors`、`pandas`、`pyarrow` |
| Node 18+ 与前端构建产物 | 仅 #1 需要 | **必须**（交 Flask 托管） |
| `handoff/` 五个交接包 | 仅自己产物 | **必须齐备且校验通过** |
| `start_part2.sh` / `stop_part2.sh` | 可选 | **必须** |
| 网络 | HDFS/YARN UI 本机可访问即可 | 演示需外部可达（桥接网卡、服务监听 `0.0.0.0`、放行端口） |
| 职责 | 本模块开发与自测 | 全链路集成、一键复位、答辩演示 |

**（2）选择与唯一性**：全组**只指定一台**为唯一权威（保证 ADS 数据版本一致、答辩口径不冲突）；优先选 **#2（TL）的机器**——集成机的操作（收包校验、Flask、`start_part2.sh`、端到端联调）本属其职责；若该机资源不足，则改选**内存/磁盘最宽裕、最早 `check_env.sh` 全绿**的一台，但须保证 #2 可随时上机。**D1 内确定**，由 #2 记入技术决策记录。差异明细与升级检查清单见《02》§2.4。

**（3）变更与容灾**：集成机可中途更换——数据与产物经 `handoff/` 包搬迁并校验、代码经 git 拉取、HDFS 中间数据可由交接包重放，**无需重装环境**；且生成器固定随机种子、同种子重跑哈希一致，最坏情况可现场重建全部数据。

## 3. 模拟数据设计（要求 2）

> 详细设计见《04-SCML-模拟数据生成与数仓分层设计》。

### 3.1 数据规模

| 表 | 规模 | 说明 |
|---|---|---|
| `stations` | 8 个 | 充电站数量刻意控制较少，分布于**北京市** 5 个行政区 |
| `chargers` | 约 300 个 | 单站 24～48 桩，快充/慢充混合，功率 7/30/60/120 kW |
| `users` | 5,000 个 | 手机号、昵称、余额、注册时间、状态 |
| `orders` | **120,000+ 条** | 90 天充电订单，含 reserved/charging/completed/cancelled 全状态 |
| `telemetry` | **1,000,000+ 条** | 充电中桩按 **5 分钟级**采样（功率、电量增量、事件；与 100 万条规模自洽） |
| `station_hourly_history` | 17,280 条 | 8 站 × 24h × 90 天，ML 训练历史（ODS 表 `ods_station_hourly`、DWD 表 `dwd_station_hourly`） |
| `events` / 充值记录 | 20,000+ 条 | 业务事件流 |

> **规模说明**：本规模是「单机伪分布式 + 虚拟机资源受限 + 3 天工期」下可完整重跑的演示级规模；如需放大，只调 `config.yaml` 的规模参数，分层与清洗逻辑不变。

### 3.2 数据质量问题场景（注入 10 类，约占总数据 3%～5%）

| # | 问题类型 | 注入方式（示例） | 真实场景类比 |
|---|---|---|---|
| Q1 | 缺失值 | `orders.ended_at` 为 NULL 但状态为 completed；`telemetry.power_kw` 缺失 | 设备上报丢包 |
| Q2 | 重复记录 | 同一订单整行重复；同一遥测帧重复推送 | 网络重传 |
| Q3 | 异常值 | `energy_kwh` 为负数或 9999；`power_kw` 超额定功率 10 倍 | 传感器故障 |
| Q4 | 格式不一致 | 时间混用 `2026-06-01T08:00:00+08:00`、`2026/06/01 08:00:00`、Unix 时间戳 | 多源系统对接 |
| Q5 | 逻辑矛盾 | `ended_at < started_at`；`busy_count > pile_count` | 程序 bug |
| Q6 | 金额口径错误 | 部分 `amount_fen` 以「元」混入（数值小 100 倍）；金额 ≠ 单价 × 电量 | 单位混淆 |
| Q7 | 孤儿引用 | 订单引用不存在的 `charger_id` / `user_id` | 外键缺失的历史库 |
| Q8 | 非法字段值 | 手机号 10 位或含字母；状态值出现 `unknown` | 录入错误 |
| Q9 | 经纬度越界 | 站点坐标超出城市范围（如纬度 > 90） | GPS 漂移 |
| Q10 | 文本脏数据 | 站名/地址含乱码、前后空格、全半角混杂 | 多系统编码不一致 |

每类问题注入比例、随机种子、命中记录数写入生成日志，保证 PySpark 探查结果可对照、可验证。

## 4. 数据质量发现与清洗设计（要求 3、4）

> 详细设计见《03-PRL-数据质量检测与清洗设计》。

### 4.1 质量发现（PySpark Profiling）

对 ODS 层每张表输出两类报告：

1. **统计画像**：行数、空值率、唯一值数、数值列 min/max/均值/分位数、时间列范围。
2. **规则检测**：针对 3.2 节 10 类问题编写检测规则（Spark DataFrame 过滤 + 计数），输出每类问题的命中数、样本记录、问题率。

产出：`quality_report.json` + 大屏主页「数据质量」面板的可视化数据，接口 `GET /api/quality/summary`（见《01》§3.1、《02》§3.3）。

### 4.2 数据清洗（PySpark）

| 问题 | 清洗策略 |
|---|---|
| 缺失值 | 关键字段（订单时间、金额）缺失 → 剔除；非关键字段（昵称）→ 默认值填充 |
| 重复记录 | 按业务主键（订单 id、telemetry(charger_id, recorded_at)）去重，保留首条 |
| 异常值 | 按物理约束剔除（电量 ≥ 0 且 ≤ 单次上限、功率 ≤ 额定功率） |
| 格式不一致 | 统一解析为 ISO 8601 `+08:00`；无法解析 → 剔除 |
| 逻辑矛盾 | `ended_at < started_at` 等违反状态机的记录 → 剔除 |
| 金额口径 | 以「单价 × 电量」重算校验，偏差 > 阈值按规则修正或剔除 |
| 孤儿引用 | 与维度表 left join，无匹配 → 剔除并计数 |
| 非法字段 | 正则校验手机号、枚举校验状态，非法 → 剔除/修正 |
| 经纬度越界 | 城市 bounding box 校验，越界 → 剔除 |
| 文本脏数据 | trim、全半角统一、乱码记录剔除 |

清洗产出 DWD 层，并生成**清洗前后对比报告**（各表清洗前/后行数、各类问题处置量），作为答辩证据。

## 5. 数仓分层设计（要求 5）

> 详细设计见《04-SCML-模拟数据生成与数仓分层设计》。

### 5.1 分层总览

| 层 | 命名 | 内容 | 加工方式 |
|---|---|---|---|
| ODS | `ods_*` | 生成器输出的原始 CSV/JSON 原样入 HDFS，**保留全部脏数据** | 直接上传，分区按日期 |
| DWD | `dwd_order_detail`、`dwd_telemetry_detail`、`dwd_station_hourly`、`dim_users`、`dim_stations`、`dim_chargers`、`dim_date` | PySpark 清洗后的明细 + 维度拉宽（**#3 主责**；`dim_date` 由 #4 生成） | 清洗作业 + 维度关联 |
| DWS | `dws_station_day`、`dws_charger_day`、`dws_user_day`、`dws_region_day`（**#5 分担**） | 按站点/桩/用户/区域 × 日 汇总：订单数、电量、营收、利用率、峰谷 | SparkSQL group by 聚合 |
| ADS | `ads_revenue_overview`、`ads_station_ranking`、`ads_user_profile_rfm`、`ads_peak_hour`、`ads_gov_service`（**#5 分担**）、`ads_charger_health`、`ads_forecast_result`（选做/#5） | 面向四类视角的应用指标；结果落 **SQLite 单文件 `ads.db`**（Parquet 存 HDFS + 导出 SQLite） | SparkSQL 汇总 + 窗口函数 |

### 5.2 关键指标口径（沿用第一阶段定义）

- 在线率 = (总桩数 − 故障桩) / 总桩数 × 100%
- 利用率 = (预约 + 充电中桩) / 总桩数 × 100%
- 金额一律整数分，展示层除 100 转元
- 时间一律 `+08:00` ISO 8601

### 6.1 页面结构：1 个主页 + 4 个视角子页

| 页面 | 面向角色 | 核心问题 | 主要图表（ECharts） |

| **主页 · 综合运营大屏** | 所有使用者 / 答辩演示入口 | 业务整体健康度 | KPI 卡片（总营收/总电量/总订单/在线率）、**北京市**站点地图散点、近 30 日营收趋势、24h 负荷曲线、桩状态环图、站点利用率排行、**数据质量面板**、实时事件流 |
| **用户视角页** | 电动车主 | 去哪里充电性价比高、不排队 | 站点价格对比、距离-价格散点、各站空闲桩实时/预测（选做）、低拥堵推荐榜、充电价格时段热力图 |
| **充电站视角页** | 站点运营者 | 站点分布与配置是否合理 | 单站利用率时段曲线、峰谷分布、快慢充结构、设备健康（故障率）、区域内站点覆盖与选址分析 |
| **企业视角页** | 企业运营决策者 | 营收最大化 | 营收/订单/电量趋势、站点营收排行、用户增长与活跃、用户 RFM 画像、客单价分布、月度经营汇总 |
| **政府视角页** | 政府监管部门 | 充电设施是否服务好民生 | 区域覆盖密度、各行政区服务指标、充电量与等效碳减排、高峰时段全城负荷、设施利用率公平性 |

### 6.2 技术要点

- Flask 提供 REST API，直接查询 ADS 层结果表（Parquet/导出 JSON），按页面划分接口命名空间。
- Vue3 单页应用，主页为全屏大屏风格（暗色主题、自适应缩放），子页面为分析看板风格，统一导航。
- ECharts 5：折线/柱状/饼环/散点/热力/地图散点；关键页面展示「数据生成时间」与「模拟数据」标注。
- 预测模块（选做）：主页与用户页展示未来 1h/6h/24h 负荷与空闲桩预测曲线；无预测结果时显示「暂无预测」。

## 7. 智能预测子系统设计（要求 7，选做）

> 详细设计见《05-PE-SparkMLlib智能预测设计》。**本任务保留「选做」标注，但小组按必做标准完成。**

- **数据源**：DWD 层 `dwd_station_hourly` 明细（8 站 × 90 天 × 小时级，源自第一阶段 `station_hourly_history`）。
- **特征**：小时、星期、是否周末/节假日、温度，以及 1h/24h 滞后与 6h/24h 滚动统计（与第一阶段口径一致）。
- **模型**：Spark MLlib `GBTRegressor` / `RandomForestRegressor`，目标为站点负荷 `load_kw` 与占用桩数 `busy_count`；空闲桩 = 总桩数 − 预测占用。
- **切分**：按时间顺序 train/valid/test，禁止随机打乱与未来泄漏；以「昨日同时刻」seasonal-naive 为基线。
- **评估**：MAE、RMSE、WAPE，与基线对比；物理约束（非负、占用 ≤ 总桩数、无 NaN）。
- **落地**：预测结果写 `ads_forecast_result`，Flask `/api/forecast/*` 供大屏调用；标记未来 24h 负荷最大的连续 2h 高峰与 80% 占用率高拥堵预警。

## 9. 测试与验收

1. 数据规模验收：订单 ≥ 10 万、遥测 ≥ 100 万，站数 ≤ 10。
2. 质量注入验收：10 类问题在注入日志与 PySpark 探查报告中一一对应。
3. 清洗验收：DWD 层无 NULL 关键字段、无重复主键、无物理越界、无孤儿引用。
4. 分层验收：ODS→DWD→DWS→ADS 逐层行数/金额可 reconcile（如 DWS 营收合计 = DWD 订单金额合计，误差为 0）。
5. 接口验收：Flask 各 API 返回字段与 ADS 表一致，响应时间可接受。
6. 大屏验收：主页 + 4 子页全部渲染，数值与 ADS 一致，标注模拟数据与生成时间。
7. 预测验收（选做）：1h/6h/24h 指标完整，优于或如实对比基线，无 NaN/越界。
8. 环境验收：各成员机在本机伪分布式 Hadoop（HDFS + Spark）上运行本模块作业，集成机完成全链路；`handoff/` 交接包校验一致；如实说明为单机伪分布式、非多节点集群。
