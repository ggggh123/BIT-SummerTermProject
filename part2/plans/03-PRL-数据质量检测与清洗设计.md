# 03 · 数据质量检测与清洗设计说明书（#3 PRL）

> 承担人：#3（PRL，项目评审负责人）
> 任务性质：**第二阶段主要任务（必做）**
> 管理职责：同行评审、缺陷把关、验收签字
> 对应老师要求：（3）用 PySpark 发现数据质量问题；（4）用 PySpark 进行数据清洗
> 上游输入：ODS 层原始数据（#4 生成，含 10 类注入问题；经 `handoff/ods` 交接包提供并校验）
> 下游输出：DWD 层干净明细 + 质量/清洗报告（供 #4 分层、#1 大屏质量模块展示）

---

## 1. 模块目标

对 ODS 层原始模拟数据，用 **PySpark** 完成两件事：

1. **质量发现**：通过统计画像 + 规则化检测，系统性发现数据中存在的质量问题，输出可对照、可复核的质量报告。
2. **数据清洗**：按既定规则对每类问题执行去重、补缺、纠正、剔除、标准化，产出 DWD 层干净数据，并生成清洗前后对比报告。

同时履行 PRL 职责：组织同行评审、维护缺陷清单、对第二阶段验收签字。

## 2. 数据质量检测设计（要求 3）

### 2.1 数据质量评估框架与流程（对齐课程《数据清洗基本流程》）

**质量六维度**：对每张 ODS 表逐项体检，先形成问题清单，再决定清洗动作。

| 维度 | 含义 | 本项目检查点 | 度量 |
|---|---|---|---|
| 完整性 | 无该填未填 | `orders.ended_at`、`telemetry.power_kw` 空值 | 缺失率 = 缺失数 ÷ 总数 |
| 准确性 | 真实反映客观事实 | `energy_kwh` 为负/9999、`power_kw` 超额定 | 异常占比 |
| 一致性 | 同一数据处处一致 | 时间格式混杂、金额单位（元/分）混用 | 冲突记录数 ÷ 总数 |
| 时效性 | 数据及时、不过时 | `etl_time` 与业务日期是否匹配 | 更新滞后时长 |
| 唯一性 | 同一实体只有一条标准记录 | `orders.id`、`telemetry(charger_id, recorded_at)` 重复 | 重复率 |
| 有效性 | 符合格式与业务规则 | 手机号 11 位、状态枚举、坐标在界内 | 格式合规率 |

**六步流程**（本项目按此推进，第 4–6 步见 §3）：

数据探查 → 质量评估 → 制定清洗规则 → 执行清洗 → 清洗校验 → 质量报告与存档

> 课程讲义 4.2.10 明确「原始层（ODS）保持不动，清洗在加工层（DWD）进行」——与本设计「ODS 原样保留脏数据、DWD 清洗产出」完全一致。

### 2.2 检测框架

```text
quality/
├── profiling.py        # 统计画像：行数/空值率/唯一值/数值分布/时间范围
├── rules.py            # 10 类问题检测规则（DataFrame 过滤 + 计数）
├── run_quality_check.py # 主作业：读取 ODS → 执行画像与规则 → 输出报告
└── output/
    ├── quality_report.json   # 机器可读报告（供大屏「数据质量」面板）
    └── quality_report.md     # 人读报告（答辩证据）
```

> **ODS 读入约定**：因存在时间格式混杂（Q4）、金额单位混入（Q6），ODS 层**所有字段按 `StringType` 读入**（`inferSchema=false`），时间/数值在清洗阶段显式 `cast` 并按规则校验；避免 schema 推断被脏数据污染导致整列读失败。

### 2.3 检测规则清单（与 #4 注入场景一一对应）

| 规则 ID | 问题类型 | PySpark 检测逻辑（示例） | 涉及表 |
|---|---|---|---|
| R01 | 缺失值 | `col.isNull()` 统计关键字段空值率；`status='completed' AND ended_at IS NULL` | orders、telemetry、users |
| R02 | 重复记录 | **按契约 `primary_key` 分组判重**（orders 为 `id`；telemetry 为 `charger_id, recorded_at`）：同键同内容保留 `_row_id` 字典序最小者；同键但内容冲突者本组全部隔离 | orders、telemetry |
| R03 | 异常值 | `energy_kwh < 0 OR energy_kwh > 单次上限`；`power_kw > 额定功率` | orders、telemetry |
| R04 | 时间格式不一致 | 正则匹配 ISO 8601，统计非标准格式行数与格式类型分布 | 全部含时间字段表 |
| R05 | 逻辑矛盾 | `ended_at < started_at`；`busy_count > pile_count` | orders、station_hourly |
| R06 | 金额口径错误 | `abs(amount_fen - price × energy) > 阈值`；识别小 100 倍的「元」混入 | orders |
| R07 | 孤儿引用 | `orders left join chargers/users`，右表 id 为 NULL 计数 | orders、telemetry |
| R08 | 非法字段值 | 手机号正则 `^1\d{10}$`；状态枚举白名单校验 | users、chargers、orders |
| R09 | 经纬度越界 | 北京市 bounding box（纬度 39.4–41.1、经度 115.4–117.5）之外计数 | stations |
| R10 | 文本脏数据 | `trim(name) != name`、含不可见字符/乱码正则 | stations、users |

> **维度归属**：R01→完整性；R02→唯一性；R03→准确性；R04/R06/R08→一致性/有效性；R05/R07→一致性；R09/R10→有效性。

### 2.4 报告内容与指标定义

- 每张表：总行数、各规则命中数、问题率、样本记录（每类 ≤ 5 条）。
- 与 #4 注入日志的**对照表**：注入条数 vs 检出条数，召回率应接近 100%，差异必须书面解释。
- 结论：问题分布 Top、对下游分析的影响评估。

**指标定义（口径冻结，供对账与答辩引用）**：

- 问题率 = 该规则命中行数 ÷ 该表总行数 × 100%
- 召回率 = 检出条数 ÷ 注入条数 × 100%（对账依据，目标 ≥ 95%，差异须书面解释）
- 准确率 = 检出条数 ÷ (检出条数 + 误报条数) × 100%（误报由抽样人工复核判定）

## 3. 数据清洗设计（要求 4）

### 3.1 清洗流水线

```text
clean/
├── clean_orders.py
├── clean_telemetry.py
├── clean_station_hourly.py  # 站点小时级历史：busy_count ≤ pile_count、温度越界
├── clean_dimensions.py   # users / stations / chargers
├── run_cleaning.py       # 主编排：ODS → 清洗 → DWD（Parquet 写 HDFS）
└── output/cleaning_report.json
```

### 3.2 清洗规则（处置策略与依据）

| 问题 | 策略 | 依据 |
|---|---|---|
| 缺失值 | 关键字段（订单时间、金额、外键）缺失 → **剔除**；非关键字段（昵称、头像）→ **默认值填充** | 关键字段不可推断，剔除不影响统计口径 |
| 重复记录 | **按业务主键判重**（口径见 `contracts/quality-policy-v0.1.json` 的 `duplicate_policy`）：同键同内容保留 `_row_id` 字典序最小者 → **去重**；同键但内容冲突者本组全部**隔离**待上游确认 | 重传数据语义等价；口径由 #2 TL 于 2026-09-15 拍板，证据与三方案对比见 `contracts/Q2-duplicate-policy-decision.md` |
| 异常值 | 物理不可能值（负电量、超额定功率）→ **剔除**；单条遥测异常不影响订单金额（金额以订单为准） | 传感器故障数据不可信 |
| 时间格式 | 多格式统一解析为 `+08:00` ISO 8601；解析失败 → **剔除** | 全平台时间契约 |
| 逻辑矛盾 | `ended_at < started_at`；`busy_count > pile_count`（站点小时表）等 → **剔除** | 违反业务状态机 |
| 金额口径 | 以「站点单价 × 电量」重算：偏差 ≤1% 视为正常；识别为元单位则 ×100 **修正**；其余 → **剔除** | 金额由服务端单价计算，客户端不可信（第一阶段规则） |
| 孤儿引用 | 与维度表 join 无匹配 → **剔除并计数** | 无法归属的事实数据 |
| 非法字段 | 手机号/状态非法 → **剔除**；可修复格式（空格）→ **修正** | 录入错误不可推断 |
| 经纬度越界 | 越界站点坐标 → **仅置空该字段并保留站点记录**（`repair`）；**不整行隔离、不回填猜测坐标** | GPS 漂移；整行剔除会使该站订单/桩/遥测变成孤儿引用并触发 Q7 级联（实测站点 8→7、订单 12 万→102,332）。口径由 #2 于 2026-09-15 决定，见 `contracts/README.md` §7 第 4 条 |
| 文本脏数据 | trim、全半角统一、乱码记录 → **剔除** | 标准化 |

> **缺失机制说明（讲义 4.2.1）**：本项目注入的缺失以 **MCAR**（完全随机缺失，如设备上报丢包）为主，故按上表「关键字段剔除、非关键字段填充」处理即可。若出现 **MAR/MNAR**（缺失与其他变量或自身取值相关，如高消费用户不填金额），需改用基于其他变量的插补或专门建模；本项目暂不涉及，作为**已知局限写入质量报告**。

### 3.3 清洗校验与报告（对齐讲义的报告六要素）

- 各表清洗前/后行数、各规则处置量（剔除/修正/填充分列）。
- 清洗保留率；抽样人工复核记录（PRL 评审证据）。
- 一致性校验：清洗后订单金额合计 vs 剔除金额合计，可对账。
- **误删/误改检查**：抽样对比清洗前后记录，确认未误删有效业务数据。

**质量报告六要素**（`quality_report.md` 与 `cleaning_report.json` 必须包含，答辩可直接引用）：

1. 数据概况：数据源、数据规模、时间范围、字段清单
2. 质量评估：六维度指标（缺失率、重复率、格式合规率、异常占比等）
3. 问题清单：每类问题的数量、占比与典型示例
4. 处理动作：每类问题的处理方式与数量（删除/填充/修正明细）
5. 清洗前后对比：关键质量指标变化
6. 遗留问题与建议：无法自动处理的记录、后续监控建议

> 原则（讲义 4.2.2）：删除数据是最后手段，**「删了多少、为什么删」必须写进报告**。

## 4. DWD 输出契约（与 #4 共同冻结）

| 表 | 内容 | 约束 |
|---|---|---|
| `dwd_order_detail` | 干净订单 + 关联站点/桩/用户维度字段 | 主键唯一、时间 ISO、金额分、无孤儿引用 |
| `dwd_telemetry_detail` | 干净遥测明细 | `(charger_id, recorded_at)` 唯一、功率 ≤ 额定 |
| `dwd_station_hourly` | 站点小时级明细（`station_id, observed_at, pile_count, rated_power_kw, temperature_c, is_holiday, busy_count, load_kw`） | `(station_id, observed_at)` 唯一、`busy_count ≤ pile_count`、温度在界内 |
| `dim_users` / `dim_stations` / `dim_chargers` | 干净维度 | 唯一键、枚举合法、坐标在界内 |
| `dim_date` | 日期维度（日期、星期、是否周末/节假日） | 由 #4 生成，本模块校验 |

> 交付方式：DWD 层 Parquet 经 `handoff/dwd` 交接包交付给 #4/#5，随包附 `manifest.json`（行数 + `sha256` + `run_id`），接收方校验通过后使用（见《02》§2.4）。
>
> **责任边界**：DWD 清洗与维度拉宽由 **#3 主责**；`dim_date` 由 #4 生成、本模块校验（与《04》§3.1 一致）。

## 6. 验收标准

1. 10 类注入问题全部检出，检出数与注入日志对账，差异有书面解释。
2. DWD 层：关键字段无 NULL、业务主键无重复、无物理越界、无孤儿引用、时间/金额格式统一。
3. 质量报告与清洗报告可作为大屏「数据质量」模块数据源与答辩证据。
4. 所有作业以 PySpark 在**本机（成员机）伪分布式 Hadoop** 环境运行（非本地单机文件处理）；输入数据经 `handoff/ods` 交接包获取并校验。
